# 把 300 个节点拖顺：MPE 可视化编辑器性能工程实录

在节点较多的 Pipeline 里拖动节点，画面会出现明显的“黏滞感”：鼠标已经移过去了，节点和连线却慢半拍。避让走线、磁吸对齐和大量流程关系同时开启时，问题更容易出现。

为了把这种体感变成可以重复测量的数据，我们准备了一份 300 节点、900 条边的高密度 Pipeline，里面有分组、错误处理、跨文件引用、图片模板和平行边。除了导入速度，测试还包括拖动、定位、撤销和面板切换这些常用操作。

React Flow 的画布渲染只是其中一环。拖动一次节点，还会带动流程关系查询、连线路由、状态订阅、撤销记录和本地缓存。耗时主要出在更新范围上：一次坐标变化，让原本无关的代码也重新处理了整张图。

::: tip 先看结果
在 246 个真实 Pipeline 节点同时订阅画布状态的测试里，同样执行 300 次位置更新，耗时中位数从 `324.95 ms` 降到 `8.68 ms`。原来会发生的 900 次无效业务重渲染也降到了 0。

这个数字说明拖动期间的业务计算少了约 97.33%。它衡量的不是浏览器 FPS，不能解读为屏幕帧率提高了 37.4 倍。
:::

## 一次拖动为什么会变重

拖动时，位置变化会连续写入 MPE 的画布状态。节点卡片上的 `next`、`on_error` 等流程标签会读取连接关系；聚焦效果需要判断当前节点与选中内容是否相关；避让走线要检查路径周围的节点；开启磁吸后，还要寻找最近的对齐位置。画布上的边动画也会继续占用绘制时间。

这些功能本身都合理，问题仍然是更新范围：节点内容和连接关系没有变化，一次坐标更新却可能让所有 Pipeline 节点重新筛选整张图。鼠标移动会连续触发这条路径，小图上不明显，到了 300 节点就会积累成迟滞。

节点和连线状态集中存放在 FlowStore 中。单看一次坐标写入，它其实一直很快：三轮各 300 次更新，总耗时也只有十几毫秒。真实拖动还会继续经过状态订阅、React 渲染、SVG 路径和浏览器绘制，所以只跑 Store 无法解释最终体感。

## 缩小坐标更新的影响范围

过去，许多组件直接依赖完整的节点或连接数组。数组引用一变，它们就重新工作，不管自己关心的内容有没有变。

现在 FlowStore 会区分节点移动、节点内容修改、连接关系修改和选择变化，代码里分别用四类修订号记录。拖动只更新布局修订号；修改字段才会更新语义修订号；新增或重连边则更新拓扑修订号。

节点卡片上的流程标签只关心节点内容和连接关系。拖动期间，这两类修订号都不变，所以它不用重新查询。Anchor 引用、同名副本和聚焦关系也改为按 ID、类型或邻接边查询，不再让每个节点扫描完整数组。

300 节点、900 条边上，一轮派生查询的工作量变成了这样：

| 查询内容 | 原来的访问次数 | 现在的访问次数 |
| --- | ---: | ---: |
| Pipeline 流程标签 | 270,000 | 900 |
| 节点聚焦关系 | 270,000 | 1,800 |
| Anchor / External 同名副本 | 9,000 | 30 |

原来的实现让每个节点扫描整张图，现在改成按真实邻接边或索引读取。流程标签少了 300 倍访问，聚焦关系少了 150 倍。

维护索引会增加 Store 写入的工作量。拖动期间不再反复复制完整的节点索引，松手后才一次同步最终位置。后文的同机复测也保留了这部分新增成本。

## 避让路径复用公共数据和计算结果

MPE 有三种连线样式，其中避让走线最费计算。它要知道节点边界，判断路径会不会撞到节点，还要处理平行边和自循环。

旧实现里，900 条边会各自扫描节点，分别构造一份相同的边界数据。一帧内，公共输入会被构建 900 次。现在画布只构建一次，再交给全部边复用。

路径结果也加入了缓存。缓存不只是记住一段 SVG path 字符串，它还记录路径折点、包围盒和实际挡路的节点。移动一个无关节点时，旧路径可以继续使用；挡路节点或端点变化时，对应条目才失效。

我们把 900 条边连续请求两遍。总请求 1,800 次，路径算法实际执行 900 次，第二遍全部命中缓存。

这里暂时没有引入 Worker。主线程和 Worker 之间传递 900 条边及节点边界同样有成本。在去掉重复扫描和重复计算后，如果完整浏览器录制仍显示路径算法超出帧预算，再评估 Worker 会更有依据。

## 磁吸索引在拖动开始时建立

磁吸对齐原本会在每次鼠标移动时遍历候选节点，再比较左右边缘、水平中心、上下边缘和垂直中心。300 次查询一共检查 1,566,000 个点位组合。

新实现会在拖动开始时建立排序坐标桶。鼠标移动时，用二分查找找到最近的桶，每次最多检查 12 个，不再随着节点数线性增长。

| 300 次磁吸查询 | 原来 | 现在 |
| --- | ---: | ---: |
| 候选节点访问 | 87,000 | 0 |
| 对齐点或坐标桶检查 | 1,566,000 | 3,600 |
| 拖动期间建索引 | 每次移动都隐式扫描 | 拖动开始时 1 次 |

分组是这里最麻烦的边界。拖动一个分组时，它的全部子节点都不能成为自己的吸附目标；拖动分组内的节点时，又要把相对坐标换算成画布坐标。我们用 100 组固定随机布局对照新旧算法，逐项比较最终位置和参考线，而不是只检查“看起来差不多”。

## 减少默认挂载的组件

另一部分开销来自默认挂载的组件数量。

以前每个节点都有一套右键菜单、JSON 编辑器弹窗、全局事件监听和局部状态。300 个节点就是 300 套。现在画布只保留一份，打开右键菜单时再记录目标节点和坐标。

长列表也改成按可见范围渲染。300 个节点的列表不再同时创建 300 行 DOM，1000 条日志也不会一次性全部挂载。虚拟列表只保留视口附近的行：

| 列表 | 数据总量 | 首屏实际挂载 |
| --- | ---: | ---: |
| 节点列表 | 301 行 | 12 行 |
| 后端日志 | 1,000 行 | 8 行 |
| 错误列表 | 300 行 | 11 行 |

节点预览也从“每行一个 Popover”改成了单例。鼠标停留超过 300 ms 后才创建预览内容和图片订阅。嵌入日志中的 payload 默认不格式化，用户展开那一条时再做。

调试、AI 历史和业务架构面板关闭后，内部内容会随之卸载。后台调试仍然可以运行，隐藏的界面不再订阅整张图。

## 合并重复的图片请求

压力数据里有 40 个图片节点，实际只引用 10 个文件，每个文件重复出现 4 次。

过去，一张图片返回会通知全部 40 个图片节点；首批图片需要 10 条 WebSocket 消息和 10 次 Store 提交。现在缓存按路径订阅，同一路径合并请求，批量响应只提交一次。

| 图片加载工作 | 原来 | 现在 |
| --- | ---: | ---: |
| 一张图片返回时收到通知的节点 | 40 | 4 |
| 首批 WebSocket 消息 | 10 | 1 |
| 首批 Store 提交 | 10 | 1 |
| 每组件请求定时器 | 40 | 0 |

Base64 转 Blob 和 Object URL 的创建也只发生在缓存写入时。图片被替换、项目切换或连接断开后，旧 URL 会被回收，避免长时间编辑后积累无主内存。

## 撤销历史从整图快照改成实体补丁

原来的撤销历史使用完整快照：每次修改都复制全部节点和边，回退时再换回旧数组。图较小时，这种实现简单直接。

到了 300 节点、900 条边，移动一个节点 100 次，就会保存 100 份几乎完全相同的图。现在历史记录使用双向实体补丁，只保存节点移动前后的位置、边的改动和实际发生的顺序变化。没有变化的实体不进入历史。

专项测试里，100 条历史的序列化体积从 20,518,200 B 降到 74,271 B，只剩原来的 0.36%。最终同机复测的数据略有不同，结果为 20,316,100 B 降到 74,964 B，比例基本一致。

删除或插入实体会引起后续数组索引整体移动。为了不把这种自然位移误判为大量 reorder，保存历史时会用最长递增子序列找出真正移动的实体。这样记录的仍是实际改动，而不是被连带改变的数组索引。

## 本地缓存按文件拆分

浏览器会保存当前打开的 Pipeline，刷新页面后可以恢复。原来的缓存结构把全部文件放在一个数组里，只改一个节点，也可能重新序列化所有已打开文件。

现在每个文件有独立记录，manifest 只保存文件顺序、当前文件和缓存协议版本。正常路径写 IndexedDB；不可用时，退回分文件的 `localStorage`。选择节点不会触发持久化，只有图内容的修订号变化才会安排写入。

拿 5 个同样大小的文件测试，单次编辑处理的数据从 1,026,151 B 降到 205,230 B，正好是原来的五分之一。页面隐藏或关闭前仍会强制提交最后一批修改，保证尚未写入的改动能够保存。

## 拖动期间暂停装饰动画

边流动和 Anchor 阴影脉冲在静止时很好看，拖动时却会和主线程、绘制线程争抢时间。现在节点拖动、画布移动、连线、边控制点拖动或页面进入后台时，装饰动画会暂停；最后一个交互结束后的下一帧再恢复。

暂停状态写在画布根节点的属性上，由 CSS 继承，不需要逐个通知节点和边。节点样式里原有的 10 处 `transition: all` 也改成具体属性，避免一次样式变化顺带检查所有可动画属性。

后台任务也做了清理。顶栏原来有两份 WebSocket 状态轮询，界面层还有重复的服务监听。现在连接状态通过同一个入口写入 Store，顶栏的活跃轮询从 2 个降到 0。页面隐藏或 MPE 卸载后，提醒定时器和监听也会清理。

## 非首屏功能改为按需加载

Monaco 编辑器、Tesseract OCR、AI Markdown、调试界面等模块体积不小，打开 MPE 后通常也不会立刻用到。它们现在改为首次使用时加载。

入口 HTML 保留了一套很轻的启动界面，主包下载时页面不会空白；React 启动后直接接管同一个节点，不会再切换一次 Loading。

| 构建产物 | 原来 | 现在 | 变化 |
| --- | ---: | ---: | ---: |
| 首屏入口 JavaScript | 5,121,573 B | 3,945,769 B | -22.96% |
| 入口 JavaScript gzip | 1,551,576 B | 1,237,152 B | -20.26% |
| 首屏 CSS gzip | 20,631 B | 17,167 B | -16.79% |
| 首屏 `modulepreload` | 2 | 0 | -100% |
| 直接首屏资源 gzip 合计 | 1,587,720 B | 1,257,235 B | -20.82% |

`dist` 总体积从 28,592 KiB 变成 28,700 KiB，增加了 0.38%。功能代码并没有减少，只是从首屏移到了首次使用。HTML 因启动界面增加约 8 KiB，gzip 后的增量为 2,178 B。

## 真实订阅测试更接近拖动体感

整轮优化完成后，我们在同一台 Apple M4、24 GiB、macOS 26.6.2 设备上重跑优化前后的代码。两边共用 Node 24.19.0、Yarn 1.22.22、Vite 7.3.0、依赖和数据集，按“优化前、当前”交替执行 7 轮。

先看纯 Store：

| 指标 | 优化前中位数 | 当前中位数 | 变化 |
| --- | ---: | ---: | ---: |
| small 导入 | 5.960 ms | 5.880 ms | -1.3% |
| medium 导入 | 5.180 ms | 8.530 ms | +64.7% |
| large 导入 | 8.850 ms | 10.400 ms | +17.5% |
| 3 x 300 次位置更新 | 14.740 ms | 16.400 ms | +11.3% |
| 单次位置更新 P95 | 0.017 ms | 0.019 ms | +11.8% |
| 松手同步调度 | 0.138 ms | 0.311 ms | +125.4% |
| 松手后状态稳定 | 1.678 ms | 4.331 ms | +158.1% |

纯 Store 数据确实有回退。medium 和 large 导入现在需要建立图索引、选择索引、修订号和历史基线；松手时还要完成拖动期间延迟的索引同步。这些都是新增成本。

位置更新 P95 的绝对差异只有 `0.002 ms`。对拖动流畅度影响更大的，是一次更新会不会让几百个不相关组件跟着工作。

接下来导入 large 数据，挂载 246 个 Pipeline 节点实际使用的流程关系订阅，再执行 300 次位置更新。这次除了 Store 写入，还会经过组件订阅和 React 更新，更接近拖动中的业务链路。

| 指标 | 优化前 | 当前 |
| --- | ---: | ---: |
| 300 次位置更新中位数 | 324.95 ms | 8.68 ms |
| 每次更新折算 | 1.083 ms | 0.029 ms |
| 无意义节点重渲染 | 900 | 0 |

::: details 查看 7 轮原始耗时

- 优化前：`361.62 / 603.89 / 330.65 / 324.95 / 315.80 / 308.47 / 319.83 ms`
- 当前：`8.52 / 8.85 / 8.12 / 8.71 / 8.80 / 8.64 / 8.68 ms`
:::

优化前，被拖动节点恰好有 3 条入边。它移动一次，3 个上游节点都会收到一次内容其实没变的业务更新；移动 300 次，就是 900 次。按修订号拆开订阅后，这些更新全部消失。

## 为什么没有给出浏览器 FPS

上面的 React 订阅测试还没有挂载完整 React Flow 的 SVG 和 DOM，也没有计算浏览器 Layout、Painting 与 GPU 合成。因此，`324.95 -> 8.68 ms` 不能换算成“FPS 提高 37.4 倍”。

我们确实启动了两个版本的 preview 构建，并用同一份 300 节点数据做浏览器自动化。当前版本成功挂载 300 个 React Flow 节点。麻烦出在目标节点的绝对坐标位于初始视口外。

尝试用 `Fit View` 定位时，优化前页面的渲染进程持续占满主线程，45 秒后仍无法完成 DOM 查询。这个页面又影响了同一浏览器会话中的当前版本，前后样本无法配对。随后使用隔离的 Microsoft Edge 152 Chromium 进程排查，确认导入和 DOM 挂载正常，但该进程以 headless、关闭 GPU 的方式运行，只适合查自动化问题，不能当作用户设备的渲染帧率。

所以这次没有给出 FPS 和 Long Task 百分比。下一轮测试需要先提供按节点 ID 稳定居中的测试入口，让两个版本都绕开 `Fit View`，再在同一有界面的浏览器里交替拖动，每种走线模式至少录三次。在此之前，现有浏览器样本不足以支持帧率结论。

## 性能之外的行为校验

图索引可能漏更新，路径缓存可能不失效，历史补丁可能撤销错对象，虚拟列表也可能遗漏导出数据。测试重点放在这些容易出现行为差异的地方。

项目准备了 100、200、300 节点三档固定数据，文件有 SHA-256 漂移检查。每个节点都带坐标，导入时不应该触发自动布局。测试场景固定使用 `Perf_Node_0050`，拖动轨迹也是固定的 600 px、300 px、返回起点。

图索引会和直接扫描的结果逐项比较。磁吸使用 100 组固定随机布局对照新旧算法。路径缓存覆盖新障碍进入、旧障碍移动、端点变化、平行边和删除。历史测试包含节点、边、Group、导入、分支、动态上限和撤销重做。缓存还要经过 IndexedDB 失败、旧格式迁移和关闭前提交。

随着实施推进，Editor 全量测试从早期 76 个文件、302 项增长到 116 个文件、437 项。最终全部通过，TypeScript、ESLint、生产构建和数据集校验也在每个阶段重复执行。图片批量协议同时跑了 LocalBridge 的 Go 测试。

## 试过但没有采用的方案

React Flow 的 `onlyRenderVisibleElements` 可以减少不可见节点对应的 DOM。实际试验碰到了 Group、跨视口长边、框选、MiniMap 和 `fitView` 的行为问题，于是回滚。要重新启用它，需要先解决这些交互差异。

iframe 变更通知也评估过命令式订阅。部分宿主依赖拖动中的实时位置消息，收窄通知会改变既有时序，因此没有实施。

这两项在计划里分别标为“暂缓”和“不实施”，没有计入本轮成果。
