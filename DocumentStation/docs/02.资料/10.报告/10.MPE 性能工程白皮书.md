# MPE 性能更新：让大 Pipeline 回到手感

MPE 1.9.3 带来一轮大规模 Pipeline 性能更新。

它解决的是一个很具体的问题：当 Pipeline 变大，编辑器是否仍能及时响应操作。

这次更新带来的变化集中在几个操作上：

- 在 300 个节点的 Pipeline 里拖动节点，节点位置和连线更新延迟更低。
- 打开避让走线和磁吸对齐时，搜索范围不会随着整张图线性膨胀。
- 关闭的调试、AI 历史和业务架构面板不再留在后台处理画布状态。
- 图片、撤销历史和本地缓存只处理实际发生变化的内容。
- 首屏先加载编辑所需的部分，Monaco、OCR 等重型功能在第一次使用时再来。

这轮更新的目标是减少大图编辑过程中的额外计算和响应延迟。

::: tip 先看结果
在 246 个真实 Pipeline 节点同时订阅画布状态的测试里，同样执行 300 次位置更新，耗时中位数从 `324.95 ms` 降到 `8.68 ms`。原来会发生的 900 次无效业务重渲染降到了 0。

这意味着拖动期间需要做的业务计算少了约 97.33%。它还不是浏览器 FPS：测试没有把完整的 SVG、DOM、Layout、Painting 和 GPU 合成算进去，所以不能把它说成“帧率提高了 37.4 倍”。浏览器层的结果和当前已验证的业务链路，我们分开报告。
:::

## 为什么做这次更新

小 Pipeline 会掩盖很多问题。几十个节点时，一次坐标变化让其他组件多做一点工作，通常感觉不出来；当图里出现分组、错误处理、跨文件引用、图片模板和平行边，鼠标移动就会把这些额外工作放大。

这次更新从用户会遇到的 300 节点场景出发。我们准备了 100、200、300 节点三档固定数据，正式样本使用 300 个节点、900 条边；拖动、定位、撤销、面板切换都用固定动作测试。每个节点都有预先写入的坐标，导入时不触发自动布局。

这样可以把两件事分开：数据结构本身增加了多少成本，以及一个坐标变化到底会唤醒多少无关组件。

## 拖动响应：按修订类型触发订阅

拖动时，位置变化会连续写入 MPE 的画布状态。节点卡片上的 `next`、`on_error` 等流程标签会读取连接关系；聚焦效果需要判断当前节点与选中内容是否相关；避让走线要检查路径周围的节点；开启磁吸后，还要寻找最近的对齐位置。过去这些组件直接依赖完整的节点或连接数组，数组引用一变就重新工作。

现在 FlowStore 区分节点移动、节点内容修改、连接关系修改和选择变化，分别记录四类修订号。拖动只更新布局修订号；修改字段才会更新语义修订号；新增或重连边则更新拓扑修订号。

节点卡片上的流程标签只订阅节点内容和连接关系。拖动期间，这两类修订号不变，流程标签不会重新查询。Anchor 引用、同名副本和聚焦关系也改为按 ID、类型或邻接边查询，不再让每个节点扫描完整数组。

300 节点、900 条边上，一轮派生查询的工作量变成了这样：

| 查询内容                   | 原来的访问次数 | 现在的访问次数 |
| -------------------------- | -------------: | -------------: |
| Pipeline 流程标签          |        270,000 |            900 |
| 节点聚焦关系               |        270,000 |          1,800 |
| Anchor / External 同名副本 |          9,000 |             30 |

原来的实现让每个节点扫描整张图，现在改成按真实邻接边或索引读取。流程标签访问量减少 99.67%，聚焦关系减少 99.33%，Anchor / External 同名副本减少 99.67%。

维护索引会增加 Store 写入的工作量。拖动期间不再反复复制完整的节点索引，松手后才一次同步最终位置。测试结果包含了这部分新增成本。

## 连线路由：复用公共数据和缓存结果

MPE 有三种连线样式，其中避让走线最费计算。它要读取节点边界，判断路径是否经过节点，还要处理平行边和自循环。旧实现会在每次路径更新时扫描整张图。

旧实现里，900 条边会各自扫描节点，分别构造一份相同的边界数据。一帧内，公共输入会被构建 900 次。现在画布只构建一次，再交给全部边复用，公共输入构建量减少 99.89%。

路径结果也加入了缓存。缓存记录路径折点、包围盒和实际挡路的节点。移动一个无关节点时，旧路径可以继续使用；挡路节点或端点变化时，对应条目才失效。

我们把 900 条边连续请求两遍。总请求 1,800 次，路径算法实际执行 900 次，计算量减少 50%；第二遍请求的缓存命中率为 100%。

## 磁吸查询：拖动开始时建立索引

磁吸对齐原本会在每次鼠标移动时遍历候选节点，再比较左右边缘、水平中心、上下边缘和垂直中心。300 次查询一共检查 1,566,000 个点位组合。

新实现会在拖动开始时建立排序坐标桶。鼠标移动时，用二分查找找到最近的桶，每次最多检查 12 个，不再随着节点数线性增长。

| 300 次磁吸查询     |               原来 |            现在 |
| ------------------ | -----------------: | --------------: |
| 候选节点访问       |             87,000 |               0 |
| 对齐点或坐标桶检查 |          1,566,000 |           3,600 |
| 拖动期间建索引     | 每次移动都隐式扫描 | 拖动开始时 1 次 |

分组场景需要额外处理：拖动分组时，子节点不能成为吸附目标；拖动分组内的节点时，要把相对坐标换算成画布坐标。我们用 100 组固定随机布局逐项比较最终位置和参考线。坐标桶检查量从 1,566,000 次降到 3,600 次，减少 99.77%；候选节点访问从 87,000 次降到 0。

## 界面挂载：复用单例并按可见范围渲染

拖动之外，另一部分开销来自默认挂载的组件数量。

以前每个节点都有一套右键菜单、JSON 编辑器弹窗、全局事件监听和局部状态。300 个节点就是 300 套。现在画布只保留一份，打开右键菜单时再记录目标节点和坐标。

长列表也改成按可见范围渲染。300 个节点的列表不再同时创建 300 行 DOM，1000 条日志也不会一次性全部挂载。虚拟列表只保留视口附近的行：

| 列表     | 数据总量 | 首屏实际挂载 |
| -------- | -------: | -----------: |
| 节点列表 |   301 行 |        12 行 |
| 后端日志 | 1,000 行 |         8 行 |
| 错误列表 |   300 行 |        11 行 |

节点预览也从“每行一个 Popover”改成了单例。鼠标停留超过 300 ms 后才创建预览内容和图片订阅。嵌入日志中的 payload 默认不格式化，用户展开那一条时再做。列表首屏挂载量从 301 / 1,000 / 300 行降到 12 / 8 / 11 行，分别减少 96.01%、99.20% 和 96.33%。

调试、AI 历史和业务架构面板关闭后，内部内容会随之卸载。后台调试仍然可以运行，隐藏的界面不再订阅整张图。

## 图片请求：复用相同路径的结果

压力数据里有 40 个图片节点，实际只引用 10 个文件，每个文件重复出现 4 次。这个例子很小，却能说明“组件各自做一遍”为什么会把网络和 Store 一起拖慢。

过去，一张图片返回会通知全部 40 个图片节点；首批图片需要 10 条 WebSocket 消息和 10 次 Store 提交。现在缓存按路径订阅，同一路径合并请求，批量响应只提交一次。

| 图片加载工作                 | 原来 | 现在 |
| ---------------------------- | ---: | ---: |
| 一张图片返回时收到通知的节点 |   40 |    4 |
| 首批 WebSocket 消息          |   10 |    1 |
| 首批 Store 提交              |   10 |    1 |
| 每组件请求定时器             |   40 |    0 |

Base64 转 Blob 和 Object URL 的创建也只发生在缓存写入时。图片被替换、项目切换或连接断开后，旧 URL 会被回收，避免长时间编辑后积累无主内存。按压力数据计算，图片通知、WebSocket 消息和 Store 提交都减少 90%，每组件请求定时器减少 100%。

## 撤销记录：保存实体补丁

原来的撤销历史使用完整快照：每次修改都复制全部节点和边，回退时再换回旧数组。图较小时，这种实现简单直接。

到了 300 节点、900 条边，移动一个节点 100 次，就会保存 100 份几乎完全相同的图。现在历史记录使用双向实体补丁，只保存节点移动前后的位置、边的改动和实际发生的顺序变化。没有变化的实体不进入历史。

专项测试里，100 条历史的序列化体积从 20,518,200 B 降到 74,271 B，减少 99.64%，只剩原来的 0.36%。最终同机复测的数据略有不同，结果为 20,316,100 B 降到 74,964 B，比例基本一致。

## 本地缓存：按文件保存修改

浏览器会保存当前打开的 Pipeline，刷新页面后可以恢复。原来的缓存结构把全部文件放在一个数组里，只改一个节点，也可能重新序列化所有已打开文件。

现在每个文件有独立记录，manifest 只保存文件顺序、当前文件和缓存协议版本。正常路径写 IndexedDB；不可用时，退回分文件的 `localStorage`。选择节点不会触发持久化，只有图内容的修订号变化才会安排写入。

拿 5 个同样大小的文件测试，单次编辑处理的数据从 1,026,151 B 降到 205,230 B，减少 80%，正好是原来的五分之一。页面隐藏或关闭前仍会强制提交最后一批修改，保证尚未写入的改动能够保存。

## 交互期间：暂停装饰动画

边流动和 Anchor 阴影脉冲在静止时很好看，拖动时却会和主线程、绘制线程争抢时间。现在节点拖动、画布移动、连线、边控制点拖动或页面进入后台时，装饰动画会暂停；最后一个交互结束后的下一帧再恢复。

暂停状态写在画布根节点的属性上，由 CSS 继承，不需要逐个通知节点和边。节点样式里原有的 10 处 `transition: all` 也改成具体属性，避免一次样式变化顺带检查所有可动画属性。

后台任务也做了清理。顶栏原来有两份 WebSocket 状态轮询，界面层还有重复的服务监听。现在连接状态通过同一个入口写入 Store，顶栏的活跃轮询从 2 个降到 0。页面隐藏或 MPE 卸载后，提醒定时器和监听也会清理。

## 首屏资源：按需加载重型功能

打开 MPE 时，用户通常只是想先看见画布、打开文件、拖一个节点。Monaco 编辑器、Tesseract OCR、AI Markdown、调试界面等模块体积不小，却不一定马上用到，所以它们改为首次使用时加载。

入口 HTML 保留轻量启动界面，主包下载时页面不会空白；React 启动后直接接管同一个节点。首屏直接加载的资源 gzip 总量从 1,587,720 B 降到 1,257,235 B，减少 20.82%；首屏 `modulepreload` 从 2 个降到 0。功能代码转移到首次使用时加载，`dist` 总体积增加 0.38%。

## 测试结果

整轮优化完成后，我们在同一台 Apple M4、24 GiB、macOS 26.6.2 设备上交替执行优化前后的代码，各跑 7 轮。导入和纯 Store 写入有小幅回退，原因是新增了图索引、选择索引、修订号和历史基线；单次位置更新 P95 只增加 `0.002 ms`。

对拖动延迟影响更大的是组件订阅和 React 更新。我们导入 large 数据，挂载 246 个 Pipeline 节点的流程关系订阅，再执行 300 次位置更新：

| 指标                 |    优化前 |     当前 |
| -------------------- | --------: | -------: |
| 300 次位置更新中位数 | 324.95 ms |  8.68 ms |
| 每次更新折算         |  1.083 ms | 0.029 ms |
| 无意义节点重渲染     |       900 |        0 |

优化前，被拖动节点有 3 条入边。它移动一次，3 个上游节点都会收到一次内容未变化的业务更新；移动 300 次，就是 900 次。按修订号拆开订阅后，这些更新不再触发，相关重渲染减少 100%。

## 结论

这轮更新把坐标变化、连线计算、图片请求、面板挂载、历史记录和本地缓存拆成了不同的工作路径。对 300 个节点的 Pipeline，已验证的业务订阅耗时从 `324.95 ms` 降到 `8.68 ms`，无意义节点重渲染从 900 次降到 0 次。

结合即将到来的 MPE APP，MPE 的性能将为您在大规模节点下带来如同初见的丝滑体验！
