# MPE 2.0：行至此刻

![MPE 2.0：行至此刻——吉祥物与伙伴踏上漫长旅途](/images/reports/mpe-2-journey-v2.png)

_写在 MPE 2.0 发布之际_

MPE 2.0 即将发布。自上线一年多，MPE 收获近 400 stars，月访问量稳定在 3500+，日活 uv 50+，并保持高频迭代——一个小而美的工具，正在变成社区的基础设施。

在 MPE 2.0版本，我们**把原本分散的项目工作接到了一起**：重构后的 Desktop 承载本地开发，Pipeline 与 PI 可以在 MPE 中一同编辑，文字识别验证工具帮助检查配置，MfwTaskRunner 则让编辑后的任务直接运行。MPE 从一张 Pipeline 画布，逐渐长成了覆盖资源项目编辑、验证与运行的工作台。

回头看，从 YAMaaPE 到今天，其实并没有一张早就画好的路线图。从创建仓库伊始，MPE 想做的只是让 MFW 项目编辑起来更加顺手的小工具，满足 MPE 开发者项目的个人需求。但随着越来越多用户的使用，我们也几次推翻自己熟悉的做法：项目越做越大，原来的设计装不下了；AI 发展得太快，刚做出的功能又显得局促。

对于一次次变化，每次更新弹出的日志面板记录的已经足够详细。但是真正值得回望的是这些改变发生时，**我们怎样重新认识正在做的东西**。

## YaMaaPE：从自己的项目开始

2025 年春天，**AI 的生产力还不足以应对项目级的需求**。Pipeline 的节点、连接、条件和一层层配置，仍需要开发者自己逐个编写、反复核对。YAMaaPE 正是从 [MNMA](https://github.com/kqcoxn/MaaNewMoonAccompanying) 这样手搓 Pipeline 的实践中诞生的。把它们画成图，能让原本埋在 JSON 中的关系直接出现在眼前，并让熟悉类似 UE 蓝图、状态机、ComfyUI 等编辑器的开发者不用面对成百上千的 JSON 键值对。最初的目标就是这么朴素——先做出一件自己真会用的工具。

YAMaaPE 用 Vue3 和 VueFlow 完成了这次尝试。它留下了很多我们后来仍然珍惜的经验：流程的结构可以被直观地表达，编辑动作也可以围绕这张图展开。但随着 MNMA 的实践继续、其他项目的需求进入视野，原型的边界也越来越清楚。它主要围绕 Pipeline V1 构建，对旧项目的支持有限；一些在熟悉项目里顺手的约定，放到更多资源项目中便未必成立。

我们没有沿着原来的实现一直加功能。**2025 年夏天，MaaPipelineEditor 开始重构。**这个选择意味着重新处理导入、解析、画布编辑和导出的关系，也意味着要把自己的项目经验变成可以容纳不同项目的设计。[v0.5.0](https://github.com/kqcoxn/MaaPipelineEditor/releases/tag/v0.5.0) 在 8 月发布时，MPE 已经是一件从 YAMaaPE 长出来、又有意离开它原有边界的新作品。

## MPE LocalBridge：向本地延伸

重构之后，我们逐渐发现，**编辑 Pipeline 从来不是孤立的动作**。文件在本地，图片在资源目录，任务运行在设备上；画布上的一个修改，最终仍要回到真实环境中确认。这些事无法全塞进最初的网页原型，却会在每一次实际开发里出现。

于是，2025 年下半年有了 [LocalBridge](https://github.com/kqcoxn/MaaPipelineEditor/issues/23)。本地文件、设备连接、截图工具、调试能力开始沿着这座桥进入 MPE。我们一边扩展能力，一边处理同步、导入兼容、连接稳定性等不那么显眼的问题。它们很难成为发布标题，却实实在在地决定着一款软件能否陪人完成一整天的工作。

2026 年初，[MPE 1.0](https://github.com/kqcoxn/MaaPipelineEditor/releases/tag/v1.0.0) 发布。这个数字对我们有分量，因为 MPE 已经走出“把 Pipeline 画出来”的第一步：**网页中的编辑、项目里的文件和本地运行环境开始连成一体**，此时，MPE 通过优化了 7 个大版本的 MPE LocalBridge，已经能够全面接管编辑 Pipeline 时可能用到的绝大多数辅助操作。

MPE 1.0 没有让我们停下来。此后继续生长的 FlowScope、跨文件能力和一次次性能调整，都来自同一个事实：真实项目总会比演示用例复杂。

## AI 到来之后，我们也改变了想法

YAMaaPE 诞生时，AI 还不是我们开发这类工具的主要出发点。到了 2025 年下半年，AI 工具的变化开始进入我们的日常判断。12 月，MPE 加入了 [AI 节点搜索](https://github.com/kqcoxn/MaaPipelineEditor/releases/tag/v0.8.4)和[节点预测](https://github.com/kqcoxn/MaaPipelineEditor/releases/tag/v0.10.4)。那时，我们首先想到的是让 AI 帮忙找到内容、起草一个节点、缩短某个具体操作。

2026 年上半年，Agent 式的工作方式带来了另一种想象：一次请求可以包含阅读上下文、决定步骤、调用工具、观察结果，再继续下一步。MPE 也在试探这种变化。我们扩展了 AI 服务接入，做过流程探索，也尝试让调试记录由 AI 帮忙归纳。每一项尝试都在回答一个局部问题，同时也让分散的入口和上下文越来越难以协调。

受 DSH 的插件式 Agent 架构启发，[2026 年 8 月，我们移除了节点预测、流程探索等早期模块](https://github.com/kqcoxn/MaaPipelineEditor/commit/4af4e0ef)，随后开始构建 [MPE Harness](/guide/server/ai)。**我们不再为每个角落分别接入一次模型**，而是让 AI 围绕项目、画布和 PI 使用同一套上下文与工具。旧功能的消失并没有抹掉那段探索：正是做过之后，我们才更清楚自己需要怎样的基础。

我们仍在学习 AI 会把软件带向哪里，但做过这些尝试，我们也更清楚地看见：MPE 以画布和图形交互为核心，**这种形式本身并不适合与 AI 深度结合**。AI 可以直接读写 Pipeline 文件，不需要像人一样拖动节点、打开面板；硬把它放进每一步图形操作里，反而会让 MPE 失去自己的长处。我们做 MPE Harness，是为了让 AI 能在需要时参与项目工作，而不是让 AI 成为这款软件的中心。

**MPE 的主要定位仍是一款面向人的 MaaFramework 可视化审阅与编辑工具**：让复杂的项目更容易看清、修改和调试。这也是我们从 YAMaaPE 走来一直没有放下的初衷。

## 行至 2.0

今年，MPE 的工作范围又向外走了一步。Pipeline 之外还有 Interface：任务如何组织、选项如何作用于节点、编辑之后如何运行。围绕这些联系，我们做了 PI 编辑器、MfwTaskRunner，并重新构建 MPE Desktop；MPE Harness 也开始处理 PI 与 Pipeline 之间的问题。这些工作汇集到 2.0，组成了今天的 MPE。

回看这条路，YAMaaPE 是从一个项目出发的原型；MPE 的重构让我们认真面对更多项目；1.0 把编辑器接进本地开发现场；走向 2.0 时，AI 和更完整的任务配置又改变了我们对软件边界的认识。每一个阶段都留有没做完的事，也都把我们带到了下一个问题面前。

感谢在这段路上贡献代码、提出需求、报告问题和分享资源项目的每一个人，也感谢 MaaFramework 社区给了这些想法不断接受检验的机会。2.0 是一次回望，也是一张新图的起点。
