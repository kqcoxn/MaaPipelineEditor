# 编辑器性能优化计划

## 文档状态

- 状态：性能审计、`PERF-001` 与 `PERF-002` 已完成，下一实施单元为 `PERF-003`
- 审计日期：2026-08-31
- 适用范围：`Editor`
- 目标：在不减少现有功能、视觉特性、数据完整性和可配置能力的前提下，降低大规模 Pipeline 的拖动、缩放、选择、列表滚动、面板开关、保存和首次加载开销
- 维护方式：每项使用固定编号；实施后更新状态、验证结果和实测数据，不删除已完成条目

## 1. 背景与结论

用户反馈编辑器页面在内容较多时出现卡顿。代码审计表明，主要问题不是单个节点组件过于复杂，而是一次局部交互会触发多处整图订阅、整图扫描、路径重算、同步序列化和大范围 DOM 更新。

节点拖动时，React Flow 会持续产生位置变更，`FlowStore.nodes` 因此每帧获得新的数组引用。当前部分 selector、调试逻辑、嵌入通知、业务架构面板和避让边逻辑直接依赖完整 `nodes` 或 `edges`。即使 `memo` 最终阻止部分 DOM 提交，selector、`useMemo` 依赖判断及其前置计算仍然已经发生。

当前主要放大链路如下：

```text
拖动一个节点
  -> applyNodeChanges 生成新的 nodes 数组
  -> 所有依赖 nodes 的 Zustand selector 重新执行
  -> 关闭的面板仍可能处理图数据
  -> 每个 Pipeline/Anchor/External 节点执行全图查询
  -> 避让模式下每条边重建全图边界并重新寻路
  -> 嵌入模式下 App 根组件跟随 nodes 更新
  -> 拖动结束后历史记录克隆整图，本地缓存同步序列化全部文件
```

因此优化原则是减少一次状态变化的扩散范围，并让拓扑、语义、布局、选择、运行状态拥有独立的失效边界。功能本身继续保留，只改变计算发生的时机、次数和位置。

### 2.3 审计限制

实施任何优化前，应先完成 `PERF-001` 的可重复基线。没有基线时只能确认代码层面的无效工作被移除，不能准确给出帧率提升比例。

## 3. 不可破坏的功能边界

所有优化必须遵守以下约束：

1. 不通过减少节点、边、日志、历史数量或字段内容来换取性能。
2. 不改变 Pipeline 导入、编辑、导出和嵌入通信的数据语义。
3. 不删除边标签、边动画、节点阴影、模板缩略图、右键菜单、调试能力或避让走线。
4. 可以在拖动、缩放、页面不可见等暂态期间暂停纯视觉动画，但交互结束后必须恢复用户配置的效果。
5. 视口裁剪只影响 DOM 渲染，不能从 FlowStore、导出、搜索、历史记录或调试快照中删除视口外元素。
6. 避让计算可以缓存、共享或迁移到 Worker，但同一输入必须保持相同路径语义。
7. 历史记录可以改为补丁或结构共享，但撤销、重做的结果和配置数量必须保持一致。
8. 懒加载只改变资源加载时机，首次打开对应功能时必须完整可用，并提供明确的加载状态。

## 5. 详细优化项

### PERF-001 建立性能基线与回归数据集

**状态**：已完成

**目标**：让每项优化都有相同输入、相同操作和可比较结果，避免凭主观感受判断。

#### 当前问题

仓库中已有功能单元测试，但没有大规模图数据夹具、性能基准或固定的手动测量流程。生产构建只能说明代码可以构建，不能说明拖动、缩放和提交是否更流畅。

#### 实施方案

1. 增加确定性图数据生成器，至少生成以下规模：

   | 级别 | 节点数 | 边数建议 | 图片节点 | 分组层级 |
   | --- | ---: | ---: | ---: | ---: |
   | 小 | 100 | 200 | 10 | 1 |
   | 中 | 200 | 500 | 25 | 2 |
   | 大 | 300 | 900 | 40 | 3 |

2. 数据集同时覆盖 Pipeline、Anchor、External、Sticker、Group，自循环、平行边、`jump_back`、`on_error`、Anchor 引用和模板图片。
3. 固定以下手动操作脚本：
   - 连续拖动一个普通节点 5 秒。
   - 连续拖动一个含子节点的 Group 5 秒。
   - 以固定速度缩放和平移 5 秒。
   - 框选 100 个节点并移动。
   - 在三种走线模式间切换后重复拖动。
   - 打开节点列表并滚动到底部。
   - 展开 1000 条后端日志和 200 条嵌入日志。
   - 打开与关闭调试、AI 历史、业务架构和 JSON 面板。
   - 连续执行 50 次编辑，再撤销和重做。
4. 对拖动状态更新提供可快速重复的自动化测量；涉及 React 提交、边绘制或动画的优化，可在固定浏览器、固定缩放比例、固定屏幕刷新率下补充记录：
   - Performance 面板中主线程 Scripting、Rendering、Painting 时间。
   - 5 秒交互内的 Long Task 数量和最长任务时长。
   - React Profiler 的提交次数及最慢提交。
   - 交互前后 JS Heap 和 DOM 节点数量。
   - 首次加载的请求数、传输体积和可交互时间。
5. 报告同时保存绝对值和相对值。不同设备之间只比较相对变化，不直接比较绝对帧率。

#### 验收标准

- 数据生成结果稳定，相同 seed 得到相同节点、边和坐标。
- 自动化基线覆盖三档真实导入和 large 数据集连续 300 次节点位置更新。
- 每个后续优化 PR 都引用对应数据集和与当前优化层级匹配的优化前后结果。
- 功能测试使用生产构建或与生产配置等价的构建，避免开发模式额外检查影响结论。

### PERF-002 隔离关闭面板的生命周期与订阅

**状态**：已完成（`PERF-002A`、`PERF-002B` 均已完成）
**目标**：关闭的面板不处理图数据；只保留运行状态跟踪等真正需要常驻的轻量逻辑。

#### 代码证据

- `Editor/src/App.tsx:371` 始终渲染懒加载的 `DebugModal`，因此懒加载只形成分块，没有延迟到用户首次打开。
- `Editor/src/components/debug/DebugModal.tsx:183` 在 Drawer 关闭时仍调用 `useDebugModalController`。
- `Editor/src/features/debug/hooks/useDebugModalController.ts:180` 订阅完整 `nodes` 和 `edges`。
- `Editor/src/features/debug/hooks/useDebugResourceChecks.ts:62` 再次订阅完整图。
- `Editor/src/features/debug/hooks/useDebugResourceChecks.ts:118` 在依赖变化时映射并序列化完整图，然后构建资源体检请求草稿；真正发送请求虽受面板状态限制，但前置计算没有被限制。
- `Editor/src/features/debug/hooks/useDebugNodeExecutionController.ts:61` 和 `:83` 还会构造文件与图快照键。
- `Editor/src/components/panels/main/BusinessArchitecturePanel.tsx:34` 常驻订阅完整图；有架构文档时，节点移动也会触发语义签名构造。
- `Editor/src/App.tsx:346` 和 `:347` 静态挂载 AI 历史与业务架构面板，普通模式下 `showPanel` 不代表面板当前处于打开状态。

#### 性能机制

Ant Design 的 `destroyOnHidden` 只销毁 Drawer 或 Modal 的内容区域，不会阻止外层 React 组件执行 Hook。只要组件本身仍挂载，完整图 selector 和派生计算就会继续执行。

#### 实施方案

1. 将调试功能拆成两个生命周期：
   - `DebugRuntimeHost`：常驻，只保留 LocalBridge 连接丢失处理、运行状态跟踪、协议结果接收和待处理打开请求。
   - `DebugModalContent`：仅当 `modalOpen` 为真时挂载 controller、资源体检、节点执行选择器和 UI。
2. 打开调试入口时先更新轻量 store，再由 `App` 或专用 Host 条件渲染 `lazy(DebugModalContent)`。
3. 保留 `debugRunRequestBridge` 的待处理请求能力。节点右键启动调试时，即使调试分块尚未加载，请求也不能丢失。
4. 资源预检分成两类：
   - 连接后确实需要自动执行的轻量资源预检，不依赖完整图。
   - 资源体检面板所需的图快照，仅在打开 `resource-health` 面板或用户刷新时通过 `getState()` 生成。
5. 业务架构面板仅在存在 `activeDocumentRunId` 时挂载完整内容和图订阅。关闭状态只订阅布尔值。
6. AI 历史面板保留运行状态存储，但 UI、Markdown、Mermaid 和会话列表仅在打开时加载和渲染。
7. 为面板统一建立模式：外层只订阅 `open`，打开后才挂载重内容，避免每个面板自行在组件末尾返回 `null`。

#### 风险与注意事项

- 调试运行可能在抽屉关闭时继续，运行状态和协议监听不能随 UI 卸载。
- 面板重新打开时必须从 store 恢复选中会话、筛选条件、宽度和最后面板位置。
- 首次打开会发生动态加载，应显示 Spin 或 Skeleton，不能表现为点击无响应。

#### 验收标准

- 调试抽屉关闭时移动节点，调试 controller、资源健康草稿和节点执行 selector 不再执行。
- 业务架构弹窗关闭且没有活动文档时，不订阅完整 `nodes` 和 `edges`。
- 关闭调试抽屉后运行中的任务仍能完成，重新打开可看到完整结果。
- 从节点右键直接启动调试时，首次动态加载不丢失目标节点和运行模式。
- 调试面板宽度、活动页签、筛选和选中记录保持原有体验。

### PERF-003 启用 React Flow 视口裁剪

**状态**：待实施  
**目标**：只为视口附近的节点和边创建 React/SVG/HTML 渲染树，FlowStore 继续保留完整图。

#### 代码证据

`Editor/src/components/Flow.tsx:684` 的 `<ReactFlow>` 没有设置 `onlyRenderVisibleElements`。当前使用的 `@xyflow/react` 支持该属性，默认值为 `false`。

#### 实施方案

1. 为主画布设置 `onlyRenderVisibleElements`。
2. 保持 `nodes`、`edges`、搜索索引、导出、历史和调试使用完整数据，不自行过滤传给业务层的数据。
3. 确认 Group 父节点与子节点的可见性判定。父节点在视口外、子节点部分进入视口时仍应正确显示。

#### 验收标准

- 300 节点场景的 DOM 节点数量随视口可见内容变化，不再接近完整图数量。
- 缩放、平移和拖动过程中没有节点闪烁、错误卸载或边断裂。
- 全选、框选、复制、自动布局、搜索跳转、MiniMap 和 `fitView` 行为不变。
- 视口外节点仍可导出、撤销、调试和被 Anchor 引用。

### PERF-004 建立图索引、分离修订号并收窄 selector

**状态**：待实施  
**目标**：节点位置变化只影响布局消费者，不让拓扑和语义查询重复扫描整张图。

#### 代码证据

- `Editor/src/stores/flow/slices/nodeSlice.ts:80` 每次位置变化都会替换 `nodes` 数组。
- `Editor/src/components/flow/nodes/PipelineNode/useNodeFlowItems.ts:17` 每个 Pipeline 节点订阅全部边，并在 selector 中过滤全部节点。
- `Editor/src/components/flow/nodes/PipelineNode/index.tsx:50` 每个 Pipeline 节点订阅全部边，用于选中关系判断。
- `Editor/src/components/flow/nodes/AnchorNode.tsx:123` 每个 Anchor 节点过滤全部节点获取引用者，`:130` 再扫描全部节点统计同名副本。
- `Editor/src/components/flow/nodes/ExternalNode.tsx:68` 每个 External 节点扫描全部节点统计同名副本。
- `Editor/src/stores/flow/utils/coordinateUtils.ts:64` 解析父链时通过 `findNodeById` 反复线性查找。
- `Editor/src/features/ai-harness/capabilities/business-architecture/architectureModel.ts:87` 架构语义签名只关心语义和拓扑，但调用方依赖完整节点数组，位置变化仍会触发重算。

#### 性能机制

Zustand selector 会在每次 store 更新时执行。返回值最终被浅比较判定为相同，只能阻止组件重渲染，不能避免 selector 内的 `filter`、循环和 Map 构造。若 N 个节点各自扫描 N 个节点，一次位置更新会产生接近 `O(N²)` 的查询工作。

#### 实施方案

1. 在 FlowStore 或独立派生索引层维护以下结构：
   - `nodeById: Map<string, NodeType>`。
   - `nodeSemanticById`，只保存 type、label 等不随位置改变的节点摘要，供流程标签、引用和副本查询使用。
   - `outgoingEdgeIdsByNodeId: Map<string, string[]>`。
   - `incomingEdgeIdsByNodeId: Map<string, string[]>`。
   - `edgeById: Map<string, EdgeType>`。
   - `nodeIdsByTypeAndLabel`，用于 Anchor/External 副本计数。
   - 现有 `anchorReferenceIndex` 继续保留，但引用 ID 通过 `nodeById` 解析，不再过滤全部节点。
2. 为状态变化增加分段修订号：
   - `layoutRevision`：位置、尺寸、父子关系变化。
   - `topologyRevision`：节点增删、边增删、端点和 Handle 变化。
   - `semanticRevision`：节点 label、识别、动作、其他字段和边属性变化。
   - `selectionRevision`：节点或边选择变化。
3. 修订号只用于失效控制，不替代实际数据。一次 action 必须在同一个 store 更新中同步修改数据、索引和对应修订号。
4. `useNodeFlowItems` 改为按当前节点 ID 读取出边 ID，再从 `nodeSemanticById` 读取必要的 label/type。位置变化不改变返回值，也不因完整 Node 对象引用变化而失效。
5. 聚焦透明度使用共享的选中 ID Set 和邻接索引。不要在每个节点内部重新构造 `selectedNodeIds` 或扫描全部边。
6. Anchor 和 External 副本数由 `(type, label)` 计数索引提供；label 变化时增量更新。
7. 父链解析接受 `nodeById`，避免每一级父节点再次线性查找。
8. 调试资源快照和业务架构签名依赖 `semanticRevision` 与 `topologyRevision`，忽略纯位置变化。
9. 索引逻辑集中在 store action 或专用模块，禁止组件各自维护不同版本的索引。

#### 风险与注意事项

- 当前节点修改入口分散在多个 slice、导入、替换、撤销和 AI 命令中，必须覆盖所有写入路径。
- 不应在每次位置变化时重建全部 Map，否则只会把数组扫描移动到 store。
- Map 和 Set 的引用稳定性必须明确；修改后需要创建受影响分支的新引用，让 selector 能正确感知变化。
- 可以先实现全量重建用于导入/replace，再为高频增删改实现增量维护。

#### 自动测试

- 随机生成图并连续执行节点增删、改名、边重连、Anchor 修改、分组和撤销，比较索引查询与直接扫描结果。
- 验证位置和选择变化不会增加 `topologyRevision` 或 `semanticRevision`。
- 验证导入、replace、undo、redo 后索引完整。
- 为 selector 增加调用计数测试，位置变化时拓扑 selector 的结果引用保持稳定。

#### 验收标准

- 单节点拖动不再让每个节点执行全量 `nodes.filter` 或 `edges.filter`。
- Pipeline 流程标签、Anchor 引用、External/Anchor 副本数和聚焦关系与优化前一致。
- 300 节点高边密度场景中，普通贝塞尔模式的拖动开销随节点数增长明显趋于线性，而不是平方级增长。

### PERF-005 共享避让走线计算与缓存

**状态**：待实施  
**目标**：同一帧只构建一次公共避让输入，只重算受位置变化影响的边。

#### 代码证据

- `Editor/src/components/flow/edges.tsx:323` 避让模式下每条边都订阅完整 `nodes` 和 `edges`。
- `Editor/src/components/flow/edges.tsx:253` 每条边调用 `buildNodeBoundsList`、过滤 Group、扫描平行边并运行路径算法。
- `Editor/src/components/flow/edges.tsx:280` 在已生成的边界列表上再次通过 `nodes.find` 判断节点类型。
- `Editor/src/core/avoidanceUtils.ts:666` 为每个节点计算边界和绝对坐标。
- `Editor/src/stores/flow/utils/coordinateUtils.ts:64` 的父链查询会进一步放大绝对坐标计算。

当前最坏情况接近 `O(E*N² + E²)`，其中重复的公共数据构建占比很高。

#### 实施方案

1. 在画布级创建 `AvoidanceRoutingContext` 或 store 派生缓存，按 `layoutRevision` 和 `topologyRevision` 生成：
   - 排除 Group 后的 `nodeBoundsById` 和稳定数组。
   - 节点绝对坐标和尺寸。
   - 以 `source + target` 为键的平行边分组及每条边索引。
   - 邻接边集合，用于定位受拖动节点影响的边。
2. 每条边只订阅自身端点、Handle、路由结果和必要的视觉状态，不订阅完整图。
3. 第一阶段保持当前 `calculateAvoidancePath` 不变，只替换公共输入来源，从而降低改造风险。
4. 第二阶段增加路由结果缓存。缓存键至少包含：
   - 边 ID、源点和终点坐标。
   - 源/目标 Handle 方向。
   - 会阻挡该边的节点边界版本。
   - 平行边索引和数量。
   - 避让配置版本。
5. 节点拖动时优先只重算：
   - 与拖动节点相连的边。
   - 原路径包围盒与拖动节点新旧边界相交的边。
   - 其他缓存仍有效的边继续复用结果。
6. 若共享缓存后路径算法仍超过帧预算，再将纯计算部分迁移到 Web Worker：
   - 主线程以修订号提交快照。
   - Worker 返回结果时校验修订号，丢弃过期结果。
   - 拖动期间可显示上一帧有效路径，最新结果到达后替换，不能短暂删除边。

#### 风险与注意事项

- Worker 的结构化克隆也有成本，未先做共享缓存就直接迁移可能只把瓶颈换成序列化。
- 路径是否受非端点节点影响，决定缓存失效范围。必须保守失效，不能出现穿过节点的旧路径。
- 自循环、平行边、Group 子节点和未测量节点需要独立测试。

#### 验收标准

- 一次 `layoutRevision` 中 `buildNodeBoundsList` 最多执行一次。
- 平行边分组每次拓扑变化最多构建一次。
- 拖动一个节点时，没有受影响的边不会重复执行路径算法。
- 三种走线模式、控制点拖动、边标签位置和路径颜色全部保持一致。

**状态**：待实施

   - 节点新增、删除、移动、数据修改和分组变化。
   - 边新增、删除、重连、排序、属性修改和控制信息。

   - 移动只记录节点 ID 及前后位置和父节点。

7. 撤销和重做应用补丁后，同步更新 `PERF-004` 的索引和修订号。
8. 调试模式可保留断言：对小图同时应用补丁与旧快照模型，比较最终图，帮助迁移阶段发现遗漏。

- 历史系统影响面广，必须先列全所有写操作，不能只优化拖动。
- 节点 data 可能包含嵌套对象，补丁边界要明确，避免后续原地修改污染旧历史。
- 导入和切换文件应重置历史，不能跨文件应用补丁。

#### 验收标准

- 单节点移动历史大小与整图节点数基本无关。
- 300 节点连续移动 100 次后，历史占用显著低于完整快照方案。
- `historyLimit` 设置实际生效，10、100、1000 等值均按配置裁剪。
- 所有现有操作可正确撤销和重做，操作日志描述不变。

**目标**：避免一次选择或编辑结束在主线程同步复制当前图并序列化所有打开文件。

#### 代码证据

- `Editor/src/components/Flow.tsx:160` 的 `UpdateMonitor` 在防抖选择状态变化后调用 `localSave()`。
- `Editor/src/stores/project/fileStore.ts:240` 的 `saveFlow()` 映射完整节点和边，创建去除选择状态的新对象。
- `Editor/src/stores/project/fileStore.ts:284` 的 `localSave()` 再映射全部打开文件，并通过 `JSON.stringify` 后同步写入 `localStorage`。
- `localStorage.setItem` 是主线程同步操作；图和打开文件较大时会形成明显 Long Task。

#### 实施方案

1. 明确缓存触发语义：使用图修订号判断数据是否变化，选择变化本身不应触发完整文件持久化。
2. FlowStore 内不需要写入文件缓存的 UI 字段，在同步边界统一排除，不要为每次保存复制所有节点只为清除 `selected`。
3. 将当前文件同步与全部文件持久化拆开：
   - 当前文件变化先更新内存中的对应文件引用。
   - 持久化使用合并后的低频调度，一段连续操作只写一次。
4. 优先评估 IndexedDB：
   - 写入异步，不阻塞主线程。
   - 可以按文件记录分别更新，避免每次序列化全部文件。
   - 保留当前“刷新后恢复多文件”的能力。
5. 若短期继续使用 localStorage：
   - 仅在 dirty revision 变化时调度。
   - 使用 `requestIdleCallback` 加超时兜底，浏览器不支持时回退短任务调度。
   - 按文件缓存已序列化结果，只重新序列化变化文件。
   - 页面隐藏或关闭前执行最后一次必要提交。
6. 配置缓存和 Pipeline 文件缓存分别写入，配置变化不应要求重写全部图。

#### 风险与注意事项

- 延迟写入不能造成刷新或关闭页面时丢失最近操作。
- IndexedDB 迁移需定义初始化失败、配额不足和事务失败提示。
- 多文件切换、删除、重载和 LocalBridge 同步必须更新正确记录。

#### 验收标准

- 只改变选择状态时不执行完整图序列化。
- 单文件编辑不会重新序列化所有未变化的打开文件。
- 300 节点拖动结束后，本地缓存写入不产生明显主线程长任务。
- 刷新恢复、文件切换、删除、外部修改提示和配额错误处理保持可用。

## 6. 最小实施单元与推荐顺序

### 6.1 拆分原则

后续不再以包含多个不同热点的大批次推进。每次开发只选择下表中的一个最小实施单元，并独立完成代码、测试、构建、手动验收和性能记录。

实施单元遵循以下边界：

1. 一个单元只解决一个明确问题，或同一数据结构中无法安全分离的几个动作。
2. 同一主项可以拆成 `A`、`B` 子单元；主项只有在所有必要子单元完成后才能标记为已完成。
3. 不把“顺手处理”的无关性能改动带入当前单元。新发现的问题先补充为文档条目，再单独实施。
4. 每个单元必须保留独立的优化前后数据。不能用后续多个改动叠加后的结果反推当前单元收益。
5. 前置依赖未完成时不提前复制一套临时索引、修订号或调度器，避免后续出现两套实现。
6. 表中顺序是推荐执行序列，不要求合并到同一个版本或同一个 PR。

### 6.3 条件实施项

将避让算法迁移到 Worker 不作为 `PERF-005B` 的默认组成部分。只有完成公共输入共享和受影响边缓存后，剩余路径计算仍在 PERF-001 基线中超过帧预算，才新增 `PERF-005C`：

**状态**：未触发

- 只迁移无 DOM、无 store 副作用的纯路径计算。
- 单独测量 Worker 消息、结构化克隆和过期结果丢弃成本。
- `PERF-005C` 使用独立 PR 和独立性能记录，不与 `PERF-005B` 合并。

### 6.4 每次实施流程

每个实施单元按相同流程完成：

1. 从 PERF-001 基线中选择与本单元直接相关的场景，记录优化前结果。
2. 只修改当前单元列出的代码边界；发现依赖缺失时先停在当前边界并更新文档。
3. 增加该单元所需的单元测试或集成测试。
4. 执行自动验证和对应手动功能验收。
5. 使用相同数据集和动作记录优化后结果。
6. 更新主项与子单元状态；主项的其他子单元仍保持待实施。
7. 当前单元独立验收后再选择下一个已满足依赖的单元。

## 8. 完成定义

单个优化项只有同时满足以下条件才能标记为“已完成”：

1. 代码中的目标无效工作已经移除，而不是通过关闭用户功能规避。
2. 对应自动测试通过，新增关键派生逻辑具备测试覆盖。
3. `yarn lint` 和 `yarn build` 通过。
4. 完成与该项相关的手动功能验收。
5. 使用 PERF-001 的相同数据集记录优化前后结果。
6. 没有增加新的整图订阅、每节点全局监听或同步主线程全量序列化。
7. 文档中的状态、实测数据、实现位置和残余风险已更新。

## 10. 避免无效或方向错误的优化

以下做法不能单独解决当前卡顿主因，不应替代前述优化项：

1. **只增加 `memo` 或 `useMemo`**：当前许多组件已经使用这些 API。Zustand selector 会先执行再比较结果，selector 内的全图扫描不会因为组件最终没有提交 DOM 而消失。
2. **只调整 Vite `manualChunks`**：静态依赖仍会由入口 preload 和执行。必须先建立真实动态导入和条件挂载边界。
3. **直接关闭动画、阴影、边标签或图片**：这会减少功能或改变默认特性，不符合本计划目标。正确方案是交互期暂停、视口裁剪和按需订阅。
4. **直接把全部计算搬入 Worker**：主线程向 Worker 传输完整图同样需要克隆和调度。应先消除重复计算、建立共享输入和精确失效，再判断剩余纯计算是否值得迁移。
5. **只降低日志、历史或节点数量上限**：这只是缩小输入，没有修复列表全量渲染、历史完整克隆和同步序列化问题。
6. **在每次位置更新时重建全部索引**：这会把组件扫描转移到 store，复杂度没有本质改善。索引必须按变化类型增量维护，语义索引不能被纯布局变化失效。
7. **同时大范围重构所有热点**：性能改动需要可比较基线。应按编号逐项实施和测量，否则无法判断收益来源，也难以定位行为回归。

Ant Design 性能检查当前为 0 项，说明没有发现组件库规则层面的明显误用；这不代表页面没有性能问题。现阶段更应优先处理应用自身的图状态扩散、算法复杂度和生命周期边界，而不是更换 UI 组件库。
