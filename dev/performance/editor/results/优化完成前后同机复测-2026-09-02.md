# 编辑器性能优化完成前后同机复测

## 结论

本轮优化的主要收益不在 FlowStore 单次写入速度，而在写入之后会被放大的订阅、整图扫描、路由、DOM、历史和持久化工作量。

- 300 节点 / 900 边下，主要整图查询、磁吸比较、菜单实例和大列表挂载量下降 `90.0%` 至 `99.9%`，典型工作量缩小约 `10` 至 `900` 倍。
- 挂载 large 数据集中 246 个 Pipeline 节点的真实 `useNodeFlowItems` 订阅后，300 次位置更新的 happy-dom 交互代理耗时中位数从 `324.95 ms` 降至 `8.68 ms`，下降 `97.33%`，约为 `37.4` 倍；语义内容未变却被位置更新触发的额外 hook 重渲染从 `900` 次降为 `0`。
- 100 条大图历史的序列化体积下降 `99.63%`，约为原来的 `1/271`；5 个已打开文件中单文件改动的缓存处理量下降 `80.00%`。
- 首屏直接引用资源的 gzip 体积从 `1,587,720` 字节降至 `1,257,235` 字节，下降 `20.82%`；Monaco 和 Tesseract 的 `modulepreload` 从 2 个降为 0。
- 代价是图索引、修订号和补丁历史的维护成本。Store-only 的 300 节点拖动三轮总耗时中位数增加 `11.3%`，松手后等待一轮事件循环的状态稳定时间从 `1.678 ms` 增至 `4.331 ms`。绝对值仍低于一帧，但这是明确的微基准回归。

因此不存在一个严谨的“编辑器整体 FPS 提升 X 倍”数字。对小图或纯 Store 写入，当前版本持平或稍慢；加入真实节点业务订阅后，拖动代理基准已显示明确的数量级收益。避让、列表、图片、历史和多文件缓存的下游工作量也已下降一至三个数量级。

## 拖动交互订阅代理

针对纯 Store 基准无法代表拖动交互的问题，本次在两个临时工作树中添加同一份一次性诊断探针：真实导入 large 数据集，挂载其中全部 246 个 Pipeline 节点的 `useNodeFlowItems`，然后用 300 个独立 React `act` 边界执行位置更新。探针直接使用两个提交各自的真实 hook 和 FlowStore，不复制 selector 逻辑。

| 指标 | 优化前 7 轮 | 当前 7 轮 | 中位数对比 | 变化 |
| --- | --- | --- | ---: | ---: |
| 300 次位置更新 | 361.62 / 603.89 / 330.65 / 324.95 / 315.80 / 308.47 / 319.83 ms | 8.52 / 8.85 / 8.12 / 8.71 / 8.80 / 8.64 / 8.68 ms | 324.95 -> 8.68 ms | -97.33% |
| 每 300 次更新的额外业务 hook 重渲染 | 每轮 900 | 每轮 0 | 900 -> 0 | -100% |

优化前，位置更新使 `nodes` 数组换引用，每个 Pipeline 节点的 `targetNodes` selector 都会重新过滤整图；被拖动节点是 3 条边的目标，所以其 3 个上游节点在 300 次位置更新中共产生 900 次语义内容未变的额外重渲染。当前 hook 只订阅语义与拓扑修订号，位置变化时两者均不变，因此没有额外业务 hook 重渲染。

该结果包含裸 Store 更新和真实 Zustand/React 订阅传播，可以直接证明 PERF-004 在拖动热路径的收益。它仍不是浏览器 FPS：没有挂载 React Flow 的 SVG/DOM，也不包含 Layout、Painting 和 GPU 合成。

## 浏览器自动化尝试

本轮按用户要求启动了浏览器自动化，并在独立 Chromium 进程中加载两个 preview 构建，使用同一份 `performance-large-300.json`。当前版本真实导入成功，画布实际挂载 300 个节点；优化前版本也能完成资源加载，但导入后目标节点的绝对坐标位于当前视口外。

尝试使用 `Fit View` 或直接对视口外目标节点执行固定轨迹拖动时，优化前版本的渲染进程持续占满主线程，超过 45 秒仍无法完成 DOM 查询或动作返回。该状态属于自动化前置条件失败，不是一次有效的 5 秒拖动录制，因此没有把这次结果换算成 FPS、Long Task 或“优化前更差”的结论。当前版本在同一浏览器会话中也受到该异常页面影响，未形成可与优化前配对的 FPS 样本。

本次浏览器层结论：真实导入路径已验证；真实鼠标拖动的浏览器 FPS 尚未取得有效配对样本。拖动流畅度目前应以本报告的“拖动交互订阅代理”作为代码层证据（`324.95 -> 8.68 ms`，额外业务 hook 重渲染 `900 -> 0`），不能将其表述为显示器上的实际 FPS。

## 测量限制

本报告不给出 FPS、Long Task、React commit、Painting 或 Heap 的伪精确百分比：浏览器自动化已执行但未形成有效的前后配对拖动样本。这些指标仍需要按 `dev/performance/editor/测量操作手册.md` 在目标浏览器中手动对比；录制前应先确认两个版本均能在同一视口内定位 `Perf_Node_0050`，且渲染进程未出现持续卡死。
