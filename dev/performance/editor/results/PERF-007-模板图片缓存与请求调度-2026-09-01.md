# PERF-007 模板图片缓存与请求调度

## 实施信息

- 实施日期：2026-09-01
- 适用范围：`Editor`、`LocalBridge`
- 关联计划：`dev/plans/编辑器性能优化计划.md` 的 `PERF-007`
- 测试数据集：`performance-large-300.json`，300 个节点、900 条边、40 个图片节点、10 个唯一路径

## 实现摘要

- 所有图片组件改用稳定路径和浅比较 selector；无关路径变化仍会执行 Zustand selector，但不会触发 React 重新渲染。
- 画布节点在挂载时声明图片需求；字段和节点列表 Popover 只在打开时挂载订阅并声明需求；图片选择器只声明当前前 50 个候选项。
- 集中调度器统一完成路径去重、合批、并发限制、超时和一次重试。单图 API 也转入批量通道。
- 批量请求增加请求 ID；资源刷新、项目切换或断线会清空活动批次，旧响应不能写入当前缓存。
- 每张图片只在响应写入时执行一次 Base64 到 Blob 的转换并创建一个 Object URL；批量响应只更新一次 Store。
- 缓存替换、资源刷新、项目切换、断线和 Store 清空都会调用 `URL.revokeObjectURL`。

## 代码级性能数据

`performance-large-300.json` 的 40 个图片节点均引用一张模板图，共复用 10 个固定路径，每个路径被 4 个节点引用。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单张图片返回时的图片节点通知 | 40 | 4 |
| 首批 10 张唯一路径的 WebSocket 消息 | 10 个单图请求 | 1 个批量请求 |
| 首批响应的 Store 缓存提交 | 10 次 | 1 次 |
| 首批 10 张图片的节点通知总量 | 400 | 40 |
| 每组件请求定时器 | 40 | 0 |
| 同一路径的 URL 构造 | 每次相关组件渲染 | 缓存写入时 1 次 |

通知计数由 `localFileStore.test.ts` 使用与 large 数据集相同的 40/10/4 引用结构复测，输出为：

```text
[PERF-007] large image update notifications: 40->4
```

该数据反映状态传播和请求结构变化，不等同于浏览器 React commit、图片解码耗时或帧率实测。

## 手动验收

需要在本机使用 100、200、300 节点数据检查：

- 首次加载 10 张固定模板图，同路径重复引用只产生一个请求且全部缩略图正常显示。
- 快速缩放和平移后不重复请求已缓存图片，节点图片槽加载前后不改变布局。
- 点击节点图片能够放大预览；关闭预览、断线和切换项目后没有失效图片残留。
- 字段模板悬停预览、节点列表悬停预览和图片选择器搜索/滚动的图片、loading 与未找到状态正确。
- 模板匹配工具可以读取 Blob 缓存并正常发起匹配。
- 断线后重新连接、资源刷新和切换资源根目录能够重新请求当前项目图片，旧批次响应不会污染新项目。

## 残余风险

- `PERF-003` 尚未启用 React Flow 视口裁剪，因此当前画布仍由所有已挂载图片节点声明需求；本项已消除重复请求和无关渲染，但视口级按需挂载仍依赖 `PERF-003`。
- 浏览器 React commit、Scripting、图片解码和 Heap 指标尚未自动化，需要按 `测量操作手册.md` 使用相同设备补测。
